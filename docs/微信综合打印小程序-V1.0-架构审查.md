## 0. 结论先行

### 0.1 七个核心判断

1. **系统形态。** 一个 API 服务（模块化单体）+ 一个独立的文件处理 Worker（无外网沙箱）+ PostgreSQL + 私有对象存储，部署在一台国内云服务器上，用 Docker Compose 管理。不做微服务，不上 Kubernetes，首版不引入 Redis。V1 的真实负载是单店，难点是金额、文件版本和权限是否正确，而不是并发。Worker 单独存在，是因为它需要不同的安全边界和更大的内存，不是为了拆服务。

2. **重新定义“精准预览”。** 打印件等于用户确认的那一份 PDF，用内容哈希锁定。预览图和打印文件都从这份规范化 PDF 派生。“与 Word 完全一致”在技术上无法定义：同一份 Word 在两台电脑上分页都可能不同，不应作为验收指标。Word 转 PDF 的保真度影响的是下单转化率，不是已支付订单的正确性。

3. **Word 转换方案由实测数据决定。** 默认自建 LibreOffice，配合合法授权的字体。云端高保真转换（WPS 开放平台或腾讯云数据万象）作为可替换的备选，也作为用户认为排版不符时的按需重转。用 30 到 50 份真实样本做验证后再定案。

4. **证件照物理尺寸靠校准，不靠文件本身。** 生成精确到毫米的文件只解决一半。打印驱动的缩放、无边距打印的扩边、进纸误差决定另一半。必须做打印机校准页，用店内真实设备的实测结果决定边距、间距和缩放修正。

5. **计价是纯函数。** 金额一律用整数“分”。价格配置发布后形成不可变版本。阶梯优惠按打印面数比例分摊，采用最大余数法，保证各文件分摊之和精确等于组总额。发布前检测整档优惠造成的金额跳变。正确性由产品负责人审定的黄金测试向量定义，实现者不得修改期望值。

6. **支付三重保障。** 只认服务端验签并解密后的支付通知，或服务端主动查单的结果。每日下载微信交易账单对账。每笔支付、退款都有持久化的唯一幂等单号。订单超时时间与微信预下单的 `time_expire` 对齐；关单时先调用微信关单接口，再查单确认最终状态。

7. **店员只下载系统生成的打印文件。** 页码范围、纸张适配、黑白转灰度、双面分份和补白都写进“打印就绪 PDF”，并附作业单。店员只选择打印机和纸张，不再在打印对话框里配置这些参数。店员也不接触用户上传的原始 DOC/DOCX，以隔离宏病毒。

### 0.2 对需求文档的总体评价

业务规则成熟，首轮边界克制，适合进入架构设计。明确排除了打印机自动控制、第三方配送平台和营销体系，这个取舍是对的。

主要问题集中在四类：

- 计价口径的细节：双面按面还是按张、整档优惠跳变如何处理、计价模式的作用范围。
- 证件照从文件到实物的物理链路没有闭环。
- 外部前置条件：经营主体、微信认证、商户号、备案、小程序类目。
- 若干经营必需但未写入的能力：取件码、发票、商家主动退款、联系顾客的方式。

需求文档没有强加不合理的技术栈。需要改写的是两个容易被当成可承诺指标的表述：“转换后与原文件一致”应改为“确认件即打印件”；证件照只能承诺“按所选物理尺寸打印”，不能承诺符合各类考试或证件的官方规范。

### 0.3 建议调整的设想

| 原设想 | 调整 |
|---|---|
| 把现有本地测试服务器演进成生产系统 | 本地 HTTP、端口 3000、本地磁盘不满足小程序合法域名、文件隔离和可靠性要求。测试服务器不进入生产。可复用部分需在看到代码后再判断，大概率只是小程序选文件和上传交互的经验。 |
| 追求 Word 完美还原 | 一致性定义为“确认件即打印件”。提供字体缺失提示、按需高保真重转、直接上传 PDF 三层处理。 |
| 店员在打印对话框里按订单参数打印 | 参数全部由系统写入打印文件。手工打印模式下，人在对话框里选错彩色、单双面或缩放，是最大的差错来源。 |
| 单一订单状态里包含“异常处理中” | 支付、履约、退款各自一套状态。异常是独立标记加原因和处理记录，不占用主状态。界面显示状态由这些维度派生。 |
| 为未来预建复杂系统 | 首版不做多门店租户、插件框架、实时长连接、地图多边形配送区、AI 相关表结构。 |

## A. 产品需求审查

### A.1 已经明确且合理的部分

- 首轮目标是可实际营业、可验收的完整打印闭环：上传、预览确认、自动计价、合并下单、微信支付、商家人工打印、自提或商家自配送、取消与退款。
- 明确不纳入首轮：文字编辑器、智能证件照修图、生活照片冲印、打印机自动控制、第三方配送自动派单、会员积分与复杂优惠券、多门店连锁。文字编辑器和智能修图是后续独立专项，智能修图是未来重点。
- 购物车：每个文件独立保存规格、数量和价格；文档与证件照可以混合下单；付款前服务端重算；付款后锁定价格、打印参数和打印成品版本。
- 阶梯累计的三个分组维度已经确认：纸张尺寸、黑白或彩色、单面或双面。三个维度相同的文档跨文件合并累计打印面数。不同规格不得混合累计。计价合并不得错误合并实际用纸和双面分页。
- 文档价格支持固定单价，以及两种阶梯算法：整档优惠、分段累进。由商家在后台切换。整份文件统一黑白或彩色，不做逐页分色收费。
- 装订首轮只有不装订、订书钉、长尾夹。同一文档多份时，按实际需要装订的份数计价。
- 证件照首轮只处理用户已有照片：裁剪、构图调整、质量提示、单人像单规格自动排版、按相纸或按套餐收费。不做 AI 抠图、换底、美化。一张相纸只能是同一人像、同一规格。
- 支付不得以客户端显示的成功为准。退款以支付渠道实际结果为准，退款金额不得超过可退余额，防止重复退款，且不得改写已支付订单的原价格记录。部分退款按已分摊金额处理，不追溯提高其他项目价格。
- 权限：管理员与店员两种角色。店员默认不能改价格、审批退款、管理账号。敏感权限必须在服务端验证。
- 验收标准包含异常用例（错误文件、重复支付通知、重复退款、越权下载），并要求区分开发环境模拟与真实商户联调。

### A.2 仍有歧义的规则

下表右列是建议默认。产品负责人确认或修改即可。其中影响数据结构的几项同时列在第 F 节，确认前不要冻结对应实现。

| 规则 | 歧义 | 建议默认 |
|---|---|---|
| 双面计价单位 | 阶梯按“打印面”累计，但双面单价按面还是按张未定义；奇数页双面时最后一张的空白背面是否计费 | 统一按“面”定价。空白背面不计费。单面与双面各自独立单价 |
| 阶梯累计口径 | 是否等于“选中页数 × 份数”；文档内空白页是否计入 | 面数 = 选中页数 × 份数。文档内空白页照常计入 |
| 计价模式作用范围 | 固定价/阶梯价是全店一个开关，还是每个规格组各自配置 | 8 个规格组（A4/A3 × 黑白/彩色 × 单面/双面）各自配置模式、单价和阶梯 |
| 整档优惠跳变 | 只要求“检查”，未定义发现跳变后怎么办 | 发布时强制展示跳变区间。是否启用“封顶保护”（按更划算的门槛收费）必须由产品负责人决定，见 B.4 |
| 金额精度 | 单价是否可能小于 1 分，例如 0.075 元 | 单价以整数“分”配置。分摊用最大余数法，合计精确到分 |
| 混合页面尺寸 | 一个 PDF 内混有 A4、A3、横向、Letter 时用什么纸、如何缩放 | 每个文件选择一种纸张。所有页面等比缩小适配、自动旋转、居中，不放大。页面尺寸不一致时提示用户 |
| 页码、双面与多份 | “1-3,5”在双面且多份时，每份是否从新的一张纸开始 | 每份独立起新纸。选中面数为奇数时，双面打印自动补一张空白背面 |
| 装订限制 | 订书钉最大张数、A3 能否装订、长尾夹规格 | 每种装订配置适用纸张、最小张数和最大张数，按每一份的张数校验 |
| 证件照套餐与相纸 | 套餐数量超过一张相纸容量时是否跨多张；按相纸收费时用户可选数量范围 | 套餐定义为“N 张照片 / K 张相纸”。配置时校验一张纸的容量。套餐不得擅自加印 |
| “输出分辨率要求” | 混用了源图最低像素和打印输出 DPI | 拆成两个字段：输出 DPI（建议 300），以及提醒阈值、强提醒阈值 |
| 店员“被授权的订单” | 按订单分配，还是全部订单可见、只限制敏感操作 | 单店首版全部订单可见。敏感操作按权限点控制 |
| 退款发起方 | 只写了用户申请。商家发现文件损坏、无法制作或内容违规时的主动退款未写 | 增加“商家主动退款 / 拒单”，必须记录原因 |
| 配送费与部分退款 | 部分退款是否退配送费；退款后低于免运费门槛是否补收运费 | 部分退款不退配送费，也不追溯补收。整单退款包含配送费 |
| 价格变化与未付款 | 购物车和已创建但未付款的订单如何处理 | 购物车结算时按最新价格重算，有差异必须二次确认。已创建订单在支付有效期内保持原价 |

### A.3 需求遗漏，建议补充

- **取件凭证。** 简历、证件材料被冒领是真实风险。建议每笔订单生成 4 到 6 位取件码，店员核销后才能标记完成。
- **发票。** 学生和企业客户经常要求开票。首版可以线下人工开票，但需要确认订单是否收集抬头。
- **联系顾客。** 小程序客服消息不能由商家主动发起。文件有问题时，店员需要一个联系方式。建议配送必填手机号，自提取件选填。
- **打烊下单。** 营业状态关闭时是否允许下单并作为次日订单，页面如何提示。
- **上限。** 单文件页数、单次文件数、份数上限。这关系到排队、恶意占用和转换资源。建议见第 F 节默认值。
- **内容合规拒印。** 涉密文件、伪造证件材料等不得承印。需要“拒单并退款”，与商家主动退款是同一能力。
- **选文件入口。** 手机端小程序从微信聊天记录选文件（`wx.chooseMessageFile`）。需要引导用户先把文件发到“文件传输助手”。从聊天文件直接用小程序打开，可作为后续体验优化，不作为首轮阻塞项。

### A.4 合规与外部风险

以下只指出需要按实施时有效的官方规则核实的点，不把具体条款当成既定事实。

- **主体与支付。** 个人主体小程序不能开通微信支付。需要个体工商户或企业主体。小程序需要完成微信认证。商户号需要与小程序 AppID 绑定。
- **备案。** 小程序本身需要备案。后端域名需要 ICP 备案，备案需要国内服务器。小程序请求和支付回调必须是 HTTPS。这是最长的前置链路，应与开发并行启动。
- **经营资质。** 《印刷业管理条例》把经营性的复印、影印、打字等列入印刷经营活动。文印门店是否需要许可或备案、小程序类目需要什么资质，以当地主管部门和微信类目审核的现行要求为准。
- **个人信息。** 证件照、简历、身份证复印件属于高敏感内容。需要配置微信要求的隐私保护指引，写明保留期限，并提供删除能力。若使用第三方云转换，必须在隐私政策中告知文件会交给该服务处理。
- **字体版权。** 把 Windows 自带中文字体安装到 Linux 服务器，超出这些字体的授权范围。方正等商业字体需要单独授权。这直接影响 Word 转换方案，不能用“先装上能用的字体”解决。
- **证件照用途承诺。** 页面只能承诺按所选物理尺寸打印，并提示不同考试和证件可能有额外规范。
- **地图服务。** 多边形配送区或服务端地理编码会调用地图 Web 服务，企业商用可能产生授权费用。首版用直线距离分档或指定区域名单即可避开。

### A.5 会显著增加成本的要求

| 要求 | 成本来源 | 建议 |
|---|---|---|
| 把转换保真理解成与 Word 完全一致 | Windows 服务器加 Office，或商业转换引擎；授权和运维都高 | 改为“确认件即打印件”，用样本实测和兜底路径解决 |
| 多边形配送区域 | 地图授权、后台绘制工具 | 首版用直线距离分档，加指定小区或楼栋名单 |
| 实时向店员推送新订单 | 长连接的连接维护 | 后台约 10 秒轮询、声音提醒、企业微信群机器人 |
| 整单打包下载 | 大文件打包的内存和带宽 | 先做逐项下载和作业单。整单 ZIP 以后用后台任务异步生成 |
| 店员按订单分配权限 | 数据权限模型明显变复杂 | 首版全店订单可见 |
| 手机号一键获取 `getPhoneNumber` | 微信按次收费 | 用户手填，或从 `wx.chooseAddress` 取得 |
| 部分退款叠加阶梯分摊 | 复杂度中等，但是经营必需 | 用下单时的分摊快照退款，不追溯重算 |

## B. 核心技术难点与风险

### B.1 Word 转 PDF

根本问题是字体和排版引擎不同会导致重排，从而改变页数、内容位置，并进一步改变价格。国内用户同时使用 Microsoft Word 和 WPS。常见字体包括宋体、仿宋_GB2312、方正小标宋（公文常用）、微软雅黑、Times New Roman、Calibri。

| 方案 | 保真度 | 边际成本 | 运维 | 隐私与授权 | 结论 |
|---|---|---|---|---|---|
| LibreOffice 自建，加开源或已授权字体 | 中。普通文档通常可用。文本框、浮动图、复杂表格、域代码、缺字体时容易偏差 | 接近 0。需要约 2 到 4 GB 内存 | 需要沙箱、并发和超时控制 | 文件不出自有服务器。字体必须合规 | 推荐默认 |
| OnlyOffice 转换引擎自建 | 中上，DOCX 通常较好 | 接近 0 | 部署较重 | 社区版 AGPL 需在采用前评估 | 纳入样本对照 |
| WPS 开放平台文档转换 | 高。与国内主流编辑器同源，字体齐全 | 按次或按页 | 低 | 文件交给第三方，必须告知用户 | 推荐备选 |
| 腾讯云数据万象文档转码 | 中上，需实测 | 按页 | 低，与 COS 集成方便 | 在同一云厂商内处理 | 推荐备选 |
| Windows 服务器加 Office 或 WPS 自动化 | 最高，因为是原生程序打开 | Windows 与 Office 授权 | 高。微软不支持把 Office 作为服务端自动化组件，进程容易卡死 | 授权复杂 | 不推荐 |
| Aspose.Words 等商业库 | 高 | 年度授权费对单店偏高 | 中 | 仍然需要字体 | 单店不划算 |

推荐策略：

- 默认转换器是运行在无外网容器里的 LibreOffice。限制单次耗时和内存。每次转换使用独立的临时配置目录。
- 解析 DOCX 的字体表。服务器缺少其中字体时，预览页提示“已替换字体，请核对版式”。
- 预览页提供“排版与原文件不符”。用户确认后，可以走云端高保真重转，或改为直接上传 PDF。云端重转只为少数文件付费。
- 转换器做成可替换接口。切换供应商只改配置。
- 决策门槛：在 30 到 50 份真实样本上比较页数一致率和人工目检通过率。建议页数一致率达到或超过 95% 时默认自建，否则默认云端。这个阈值需要产品负责人确认。

### B.2 精准预览

- 预览图和打印文件都从同一份规范化 PDF 派生。规范化包括：修复结构、去掉权限密码、拒绝需要打开密码的文件、把表单和批注拍平、记录每一页的尺寸和旋转、计算 SHA-256。
- 批注是最常见的隐蔽不一致：不拍平时，预览可能显示批注而打印不显示，或相反。
- 小程序端使用服务端渲染的页面图片，按需加载。用户改页码、颜色、纸张时，客户端即时模拟“共 X 面、用纸 Y 张”，最终金额仍以服务端为准。需要看细节时，可以用 `wx.openDocument` 打开 PDF。
- 不建议在小程序 web-view 里跑 pdf.js。它需要业务域名，低端机性能差，还会再引入一层字体渲染差异。
- 大文件：限制页数和大小，预览图懒生成。几百页扫描件不应在上传时一次性渲染全部页面。

### B.3 证件照物理尺寸

精度链路是：源图像素 → 裁剪 → 按毫米排版 → 输出文件 → 打印驱动 → 打印机进纸和无边距扩边 → 裁切。前四步软件可控，后三步只能靠实测。

示例（常见参考尺寸，正式规格需商家确认）：6 寸相纸 101.6 × 152.4 mm，一寸照 25 × 35 mm。算法分别尝试照片竖放和横放，取可排数量更多的一种，网格居中。

- 边距 0、间距 0：竖放 4 列 × 4 行 = 16 张。横放只有 12 张。采用 16 张。
- 边距 3 mm、间距 2 mm：竖放 3 列 × 4 行 = 12 张。横放 10 张。采用 12 张。

几毫米的边距和间距差异，会让同一张相纸的可排数量从 16 变成 12，直接改变“按相纸收费”的性价比。打印机是否支持无边距、不可打印区域有多宽，必须用店里的设备实测后才能定默认值。

实现要点：

- 输出 PDF。页面尺寸等于相纸的精确尺寸。照片按 300 DPI 嵌入，位置按毫米计算。店员以“实际大小”打印。
- JPEG 加 DPI 元数据只作为补充。Windows 照片查看器经常自动裁切和缩放，不能作为打印文件。
- 后台生成校准页：标尺、50 mm 和 100 mm 方框、裁切线。店员实测后，为每台打印机录入 X/Y 缩放修正和安全边距。
- 客户端只提交裁剪矩形（相对原图坐标）。服务端用原图裁剪。统一处理 EXIF 方向。照片选择必须使用原图，`wx.chooseMedia` 的 `sizeType` 设为 `original`，避免微信压缩。
- 质量：有效 DPI = 裁剪区域像素宽 ÷ 照片物理宽（英寸）。一寸宽 25 mm 约 0.98 英寸，300 DPI 大约需要 295 像素。建议有效 DPI 低于 300 提醒，低于 200 强提醒。首轮的清晰度提醒不是智能修图。

### B.4 自动计价

计价实现为一个无输入输出副作用的纯函数：输入是购物车项和某一价格版本，输出是金额明细。服务端报价、后台价格模拟器、自动化测试共用这一份实现。小程序不重复实现计价公式，只调用报价接口并展示结果。

规则：

- 全部金额用整数“分”。单价不允许配置出小于 1 分的值。
- 分组键是：纸张 × 颜色 × 单双面。只有文档打印参与这三个维度的累计。证件照、装订、配送各自独立计价，不混入文档阶梯。
- 组内优惠按各文件的打印面数比例分摊，使用最大余数法：先向下取整到分，剩余的分按小数部分从大到小分配，小数部分相同时按稳定顺序分配。分摊之和必须等于组总额。
- 每次发布生成不可变价格版本。订单保存版本号和完整明细快照。之后调价不影响已支付订单，也不影响支付有效期内已创建的未支付订单。
- 部分退款按该快照中的分摊金额退，不重新把剩余商品套进新阶梯。
- 发布前运行跳变检测。整档优惠下，门槛前若干数量的总价可能高于门槛数量的总价。检测到的区间必须展示给商家。是否自动改按更划算的门槛收费（封顶保护），由产品负责人决定。

示例阶梯（说明算法，不是真实售价）：1 到 49 面每面 0.30 元，50 到 199 面每面 0.20 元，200 面及以上每面 0.15 元。

| 打印面数 | 整档优惠 | 分段累进 |
|---:|---:|---:|
| 49 | 14.70 元 | 14.70 元 |
| 50 | 10.00 元 | 14.90 元 |
| 199 | 39.80 元 | 44.70 元 |
| 200 | 30.00 元 | 44.85 元 |

同一示例的跳变区间：

- 34 到 49 面的整档总价高于 50 面。49 面是 14.70 元，50 面是 10.00 元。
- 151 到 199 面的整档总价高于 200 面。199 面是 39.80 元，200 面是 30.00 元。

分摊示例：三个文件同组，面数分别为 7、13、30，合计 50 面，采用分段累进，组总额 14.90 元（1490 分）。

| 文件 | 面数 | 按比例的精确值 | 最大余数法结果 |
|---|---:|---:|---:|
| 文件 1 | 7 | 2.0860 元 | 2.09 元 |
| 文件 2 | 13 | 3.8740 元 | 3.87 元 |
| 文件 3 | 30 | 8.9400 元 | 8.94 元 |

2.09 + 3.87 + 8.94 = 14.90。多出来的 1 分给了小数部分最大的文件 1。

测试要求：

- 黄金向量：一组 JSON 输入和期望输出，由产品负责人审定。实现者不能为了让测试通过而改期望值。
- 性质测试：分摊之和等于组总额；分段累进的总价随数量增加不下降；不同规格组互不影响；双面的空白背面不计入面数；多份时每一份的用纸独立计算。
- 这些测试直接对应验收项：跨文件累计、两种阶梯算法、购物车修改后的服务端重算、调价后已支付订单不变。

### B.5 微信支付与订单一致性

小程序支付流程：

1. 服务端用当前价格版本重算。客户端提交的期望总额不一致时，返回“价格已变化”和新明细，用户确认后才能继续。
2. 服务端向微信预下单，拿到 `prepay_id`，生成小程序调起支付所需的签名。预下单设置 `time_expire` 等于订单过期时间。
3. 小程序调用 `wx.requestPayment`。客户端返回的成功只触发一次服务端查单，不直接改订单状态。
4. 微信回调通知。服务端验签，用 APIv3 密钥做 AES-GCM 解密。核对 `appid`、`mchid`，通知金额必须等于该支付单金额。
5. 在同一个数据库事务里更新订单，并写入 outbox 事件。随后异步生成打印文件、通知店员。这些副作用失败可以重试，不能回滚已经确认的支付。

必须处理的情况：

| 风险 | 机制 |
|---|---|
| 客户端伪造“支付成功” | 只认验签解密后的通知，或服务端主动查单 |
| 重复通知 | 通知按微信通知 ID 去重；`transaction_id` 唯一约束；状态更新写成“仅当当前状态为待支付时改为已支付”，并检查影响行数 |
| 通知丢失或延迟 | 用户回到小程序时查单；定时任务查询长时间处于支付中的订单；每日下载交易账单对账 |
| 超时后用户仍然完成支付 | `time_expire` 与订单过期时间相同。关单时调用微信关单接口，再查单。若实际已支付，订单转为已支付，不能当成已取消 |
| 价格在支付前变化 | 结算时重算并要求确认。金额变化必须使用新的商户订单号，同一商户订单号不能修改金额 |
| 同一业务订单产生两笔成功支付 | 每次支付尝试使用独立的 `out_trade_no`。新建前关闭旧的支付单。若仍出现双付，自动退掉多余的一笔并告警 |
| 重复退款 | `out_refund_no` 在审批通过时生成并持久化，重试复用同一个号。可退余额在同一事务内锁定后校验 |
| 退款异常 | 同时处理退款通知和退款查询。状态“异常”进入人工处理。商户可用余额不足会导致退款失败，需要告警 |
| 金额或商户被篡改 | 通知中的金额、`appid`、`mchid` 必须与本地支付单一致，否则拒绝入账并告警 |

其他一致性约束：

- 创建订单的请求带幂等键，数据库对（用户, 幂等键）做唯一约束。
- `out_trade_no`、`transaction_id`、`out_refund_no` 都有唯一约束。已退金额有数据库检查约束：已退小于或等于已付。
- 每日对账比较微信交易账单、退款账单和本地记录。差异进入告警。对账是发现金额缺陷的可靠手段，不是可有可无的报表。

开发期测试：微信支付 V3 没有能够完整覆盖下单、通知、退款的官方沙箱（以实施时的官方说明为准）。开发期需要一个按 V3 协议签名并加密通知的模拟微信支付服务，用来做自动化测试。真实联调用 0.01 元的真实支付和真实退款完成。本地接口测试不能替代这一步。

| 小程序审核或类目不通过 | 中 | 高 | 提前按现行规则确认类目和资质。隐私接口按规范声明 |

## C. 推荐总体架构

### C.1 为什么是这个架构

推荐方案称为方案 A：模块化单体 API，加独立文件处理 Worker，加 PostgreSQL，加私有对象存储，全部容器运行在一台国内云服务器上。

选择它的原因：

- 单店的订单量不需要按服务水平扩展。拆成很多网络服务会增加部署、事务和排障成本，不能提高计价或支付的正确性。
- 订单、支付、退款必须在同一个数据库事务里保持一致。一个 PostgreSQL 比多个数据库或文档型数据库更适合。
- 文件转换必须和 API 隔离。转换进程需要无外网、只读根文件系统、非 root、内存和时间上限。这是安全边界，不是组织架构。
- Docker Compose 可以在开发机上一条命令启动同一套组件，方便多个 Agent 各自运行测试。
- 以后订单量上升时，可以先升配，再把 Worker 挪到另一台机器，再把数据库换成托管实例。业务代码不用重写。

首版明确不引入：Kubernetes、服务网格、Redis、消息队列集群、多门店租户模型、插件框架、通用工作流引擎。

### C.2 运行时组成

```text
消费者微信小程序 ──HTTPS──┐
                          ├── 反向代理（Caddy，自动证书，限流）
管理后台（店内电脑）──HTTPS─┘              │
                                          ▼
                              API 服务（模块化单体）
                         订单 · 计价 · 支付 · 退款 · 权限
                    │                │                 │
                    │                │                 │
                    ▼                ▼                 ▼
            通知渠道            PostgreSQL         微信支付 V3
     企业微信机器人、订阅消息   业务数据 + 任务队列   下单、通知、查单、退款、账单
                    ▲                ▲
                    │                │
                    └── 文件处理 Worker ┘
                     转换 · 预览 · 排版
                     容器无外网
                              │
                              ▼
                         私有对象存储
                 原件 · 确认版 PDF · 预览图 · 排版文件
```

上传不经过 API 服务器搬运文件：小程序先向 API 申请上传凭证，再把文件直传到私有对象存储。对象存储的域名加入小程序的上传合法域名。

API 与 Worker 在同一台服务器的不同容器中。Worker 容器没有外网访问。Worker 从数据库队列领取任务，从对象存储读取原件，把确认版 PDF、预览图和排版文件写回对象存储。

### C.3 技术选型

| 层 | 推荐 | 理由 | 可替代 |
|---|---|---|---|
| 小程序 | 原生小程序 + TypeScript，组件库用 TDesign 或 Vant Weapp | 只需要微信端。隐私授权、支付、选文件 API 直接可用 | 若未来要多端，再评估 uni-app 或 Taro |
| 管理后台 | Vue 3 + Vite + Element Plus | 国内生态成熟，适合快速做管理页面，Agent 也容易产出一致代码 | React + Ant Design |
| 服务端 | Node.js + TypeScript + NestJS | 与两端同一语言，类型和契约可以共享。框架约束有利于多个 Agent 产出风格一致。现有测试服务器也是 Node | Go。官方支付 SDK 和内存占用更有优势，但会拆成两种语言 |
| 接口契约 | zod schema 生成服务端校验、OpenAPI、前端类型和 Mock | 契约先行，前后端可以并行 | 手写 OpenAPI |
| 数据库 | PostgreSQL。ORM 用 Prisma 或 Drizzle | 事务、检查约束、JSON 快照、部分唯一索引。同一实例可做任务队列 | MySQL |
| 任务队列 | 基于 PostgreSQL 的队列（pg-boss 一类） | 少一个需要备份和监控的组件 | 量大以后再换 Redis + BullMQ |
| 文件存储 | 腾讯云 COS 或阿里云 OSS 的私有桶 | 便宜、签名 URL、生命周期规则 | 本地磁盘不推荐作为正式存储 |
| 文档与图片处理 | LibreOffice、qpdf、pdfium 或 poppler、pdf-lib、Ghostscript、sharp（libvips） | 开源，可以用命令行隔离，外面套可替换接口 | 云转换作为另一个实现 |
| 部署 | 国内云 2 核 4 GB 一台 + Docker Compose + Caddy | 成本低，本地和生产的拓扑一致 | 云托管或 Serverless，见方案 B |
| 观测 | 结构化日志、健康检查、云监控、企业微信机器人告警 | 单店足够 | 需要错误聚合时再加 Sentry 一类服务 |

选择 TypeScript 覆盖小程序、后台、API 和 Worker，是为了契约和类型只维护一份，也方便审查低成本 Agent 的代码。未来的智能修图服务用 Python，因为模型生态在 Python，而且它本来就应该是独立服务。

### C.4 API 内的模块

这些是同一个进程里的模块边界，不是独立部署的服务。

| 模块 | 职责 | 不允许破坏的约束 | 负责人 |
|---|---|---|---|
| identity 身份 | 小程序登录、后台账号、会话 | `session_key` 不下发到客户端 | 架构负责人 |
| files 文件 | 上传凭证、归属、签名下载、保留期清理 | 每次访问都做归属或权限校验 | 架构负责人 |
| documents 文档 | 文档项、处理状态、页数、预览 | 用户确认时绑定规范化 PDF 的哈希 | Agent 实现，接口由架构负责人定 |
| photos 证件照 | 规格、裁剪参数、质量、排版 | 长度单位一律毫米。排版是纯函数 | Agent 实现，重点审查 |
| pricing 计价 | 价格配置、版本、发布校验、报价 | 整数分。已发布版本不可变 | 架构负责人 |
| cart 购物车 | 购物车项的增删改 | 只能引用已经确认的文档项或照片项 | Agent |
| orders 订单 | 下单、快照、状态机、取件码 | 状态只能经状态机函数变更 | 架构负责人 |
| payments 支付 | 预下单、通知、查单、关单、对账 | 幂等。金额和商户标识必须校验 | 架构负责人 |
| refunds 退款 | 申请、审批、执行、结果 | 可退余额校验。退款单号唯一 | 架构负责人 |
| fulfillment 履约 | 打印就绪文件、作业单、自提和配送状态 | 文件版本与下单时的哈希一致 | Agent 实现，重点审查 |
| delivery 配送 | 区域、运费、免运费门槛 | 服务端计算，不信客户端运费 | Agent |
| admin / rbac | 角色、权限点、审计 | 敏感操作服务端鉴权 | 框架归架构负责人，页面归 Agent |
| stats 统计 | 经营统计 | 只读 | Agent |
| notifications 通知 | 企业微信机器人、订阅消息 | 通知失败不影响主流程，走 outbox | Agent |

### C.5 文件从上传到打印

1. **选择。** 文档使用 `wx.chooseMessageFile`，扩展名限定 pdf、doc、docx。照片使用 `wx.chooseMedia`，`sizeType` 为 `original`。
2. **申请上传凭证。** 服务端校验大小和配额，生成随机对象键，签发只允许该对象、限制大小、大约 10 分钟有效的直传凭证。用户原始文件名只作为显示名存入数据库，不作为存储键。
3. **直传。** 小程序把文件传到私有桶，完成后通知服务端。
4. **检查。** Worker 校验魔数（PDF、OLE、ZIP），检查 ZIP 解压比和总大小、是否加密、页数上限，计算 SHA-256。
5. **转换与规范化。** DOC/DOCX 在无外网沙箱中转为 PDF。PDF 用 qpdf 修复并去除权限密码；需要打开密码的文件直接失败。表单和批注拍平。产出确认版候选 PDF。
6. **分析与预览。** 记录每页尺寸和旋转。前几页立即生成预览图，其余按需生成。DOCX 缺字体时在预览页提示。
7. **用户确认。** 用户设置打印参数并看到页数、用纸和金额预估。点击确认后，文档项绑定该 PDF 的哈希。未确认的文件不能加入购物车。
8. **下单锁定。** 服务端重算价格。订单行保存参数、价格明细、PDF 哈希和价格版本号。
9. **打印就绪文件。** 支付成功后，Worker 按锁定参数确定性地生成：抽取页码、适配纸张、双面分份并补白、黑白订单转为灰度。附作业单（订单号、取件码、规格）。记录生成引擎版本和输出哈希。
10. **店员下载。** 后台申请大约 5 分钟有效的签名链接，并写审计日志。店员按实际大小打印。
11. **保留与清理。** 到期删除文件，保留元数据和哈希。对象存储的生命周期规则作为兜底，避免清理任务漏跑时文件永久留下。

转换失败、文件损坏、页数无法确定时，文档项停在失败状态，不能加入购物车，更不能进入已支付订单。

### C.6 订单状态

四套状态分开存储。界面上的“待自提”“退款中”等文字由它们组合得出。

| 维度 | 状态 |
|---|---|
| 订单生命周期 | 待支付 → 已支付 → 已完成。待支付 → 已取消（用户取消或超时）。已支付 → 已关闭（全额退款完成） |
| 支付状态 | 未支付、已支付、部分退款、全额退款 |
| 履约状态 | 待处理 → 打印中 → 待自提，或待配送 → 配送中 → 已完成 |
| 退款单 | 待审核 → 已批准 → 退款中 → 成功或异常。待审核 → 已拒绝 |
| 异常 | 独立标记、原因、处理记录。不占用上面的主状态 |

状态变更只能通过状态机函数，并用条件更新实现：只有当前状态符合预期时才更新，然后检查影响行数。每次变更写入订单事件表，供审计和客服查询。

### C.7 文件安全与账号权限

- 私有桶，随机对象键。下载文件名做清洗，并按 RFC 5987 编码，避免恶意文件名。
- Worker 容器无外网、根文件系统只读、非 root、限制 CPU、内存和时间。LibreOffice 禁用宏。每次转换使用独立临时配置目录。
- 消费者只能访问自己的资源。服务端用登录态里的用户标识校验归属，不信任请求体里的用户 ID。
- 后台权限点至少包括：`order.read`、`file.download`、`price.publish`、`refund.approve`、`staff.manage`。店员默认只有订单查看、文件下载、履约状态更新、异常记录。
- 每次下载记录操作者、时间和文件。签名链接短时有效。
- 后台密码使用 argon2id。登录限流，会话有过期时间。管理员账号可选 TOTP。
- 商户私钥、APIv3 密钥、小程序 AppSecret 不进入代码仓库。用权限受限的文件或环境变量注入。支持密钥轮换。验签使用的平台证书或微信支付公钥，以该商户号当时启用的模式为准。
- 隐私保护指引按实际调用的隐私接口配置。隐私政策写明文件不用于模型训练。日志对手机号、地址、文件名脱敏。用户可以删除尚未下单的文件。
- 建议的默认保留期：未下单文件 7 天；订单完成后的打印文件 30 天；证件照完成后 7 天。订单、支付、退款记录按财务需要长期保留，与文件分开。保留期做成可配置。

### C.8 后续文字编辑器与智能修图如何接入

V1 只预留接入点，不开发这两个模块。

- 订单行引用“产物”：一份规范化 PDF，或一张最终照片。订单不关心产物来自上传、编辑器还是修图。产物表有一个 `derived_from` 字段记录血缘。
- 文字编辑器以后作为独立的小程序分包和独立后端模块。它输出规范化 PDF（例如无头浏览器把 HTML 渲染成 PDF），然后进入现有的预览、确认、计价、下单。V1 的文档项保留“来源”字段即可。
- 智能修图以后是独立 Python 服务。任务接口是：输入照片产物、规格、操作列表，输出新的照片产物和质量报告。照片项改为引用输出产物后，直接复用 V1 的排版和计价。建议先用第三方人像分割 API 验证需求，再决定是否自研模型。
- 接入前需要单独评估：部分开源抠图模型禁止商用；人脸信息处理需要单独同意；美颜和人像编辑可能涉及算法或深度合成的相关规定。
- V1 的低成本预留：产物血缘字段、照片来源字段、小程序按分包组织、裁剪界面上的头部位置参考线。
- V1 不做：插件框架、通用工作流引擎、GPU 资源、任何 AI 表结构。

## D. 备选架构与成本

### D.1 三套方案

| 维度 | 方案 A（推荐）：单机模块化单体 | 方案 B：微信云开发 / Serverless | 方案 C：方案 A 的增强 |
|---|---|---|---|
| 架构 | API + Worker + PostgreSQL 容器，对象存储托管 | 云函数 + 文档型云数据库 + 云存储。转换用云托管或数据万象 | 同 A。数据库改为托管 PostgreSQL，Worker 可放到另一台机器 |
| 开发复杂度 | 中 | 起步低。金额、退款、后台事务写起来更别扭 | 中 |
| 固定月费 | 低，一台服务器 | 起步低，量大后按量费用不透明 | 中，多一项托管数据库 |
| 文档转换 | 自建，边际成本接近 0 | 更可能按页付费。云托管里跑 LibreOffice 有冷启动 | 自建，边际成本接近 0 |
| 金额一致性 | 强。关系型事务和约束 | 文档数据库的事务能力有限，退款和分摊要更小心 | 强 |
| 运维 | 需要自己做系统更新和备份 | 最少 | 较少，数据库由云厂商托管 |
| 厂商锁定 | 低。标准容器，可以迁到其他云 | 高。业务代码绑定云开发 API | 低 |
| 本地测试和多 Agent 并行 | 好。一条命令启动全套 | 较差。依赖云环境 | 好 |
| 以后接 AI 模块 | 加一个独立服务 | 需要另起云托管服务 | 同 A |
| 适用 | 单店首版，优先正确性和可控成本 | 上线后没有人能维护服务器，且接受锁定和按页转换费 | 订单量上升或对数据库可用性要求提高之后 |

取舍：

- 方案 A 用少量运维换强一致性、低锁定和可在本地完整测试。它最适合“正确性优先，并且多个 Agent 并行开发”。
- 方案 C 是 A 的升级路径。换托管数据库、把 Worker 拆到第二台机器，不需要重写业务。
- 方案 B 适合几乎没有后端维护能力、只求最快上线的情况。计价和部分退款在文档型数据库上更难写对。
- 还有一个非自建选项：购买现成的云打印 SaaS 小程序，通常按年订阅。如果目标只是开始营业，购买的前期成本低于自建。本项目把智能修图定为后续差异化能力，自建才有充分理由。这个取舍建议在正式开发前明确做一次。

### D.2 成本估算

前提：单店；日均 30 到 150 单；考试季峰值约为平时的 3 倍；平均每单 2 个文件、每个文件约 15 页、约 2 MB。下面是量级，不是报价。云服务器、对象存储、流量和支付费率以采购时的官方价格和签约费率为准。

| 类别 | 项目 | 估算 | 说明 |
|---|---|---|---|
| 一次性 | 微信认证 | 300 元/年 | 小程序开通支付的前提 |
| 一次性 | 微信支付商户开通 | 官方不收开户费 | 警惕第三方代办收费 |
| 一次性 | 域名 | 数十元/年 | |
| 一次性 | ICP 备案、小程序备案 | 免费 | 需要国内服务器。流程长，尽早启动 |
| 一次性 | HTTPS 证书 | 0 | Let's Encrypt，由 Caddy 自动续期 |
| 一次性 | 开发的模型和订阅费用 | 取决于模型和用量 | 金额、权限、状态机用强模型；页面和常规模块用低价模型 |
| 一次性，可选 | 商业字体授权 | 数千元量级 | 仅当样本测试证明公文字体是主要失败原因时才购买。按字体和用途询价 |
| 固定/月 | 云服务器 2 核 4 GB | 约百元/月量级 | 促销时可能更低。LibreOffice 需要内存，不建议 2 GB |
| 固定/月 | 对象存储（100 GB 以内）和备份 | 每月数元 | |
| 固定/月，方案 C | 托管 PostgreSQL | 约百元/月量级起 | 升级时再加 |
| 变动 | 外网下行流量 | 每月数元到数十元 | 主要是预览图和店员下载 |
| 变动 | 自建文档转换 | 0 | 占用服务器 CPU 和内存 |
| 变动 | 云端文档转换 | 单价 × 转换页数 | 用户上传后放弃下单也会产生费用。按需重转可以只为少数文件付费 |
| 变动 | 微信支付手续费 | 约 0.6% × 交易额 | 以签约费率为准。月流水 1 万元大约 60 元 |
| 变动 | 手机号快速验证 | 按次 | 建议不使用 |
| 变动 | 订阅消息、企业微信机器人 | 0 | |

方案 A 的月度固定成本是：一台服务器约百元量级，加上存储和流量数元到数十元，再加上约 0.6% 的支付手续费。方案 C 在此基础上增加托管数据库。云端转换的费用等于月转换页数乘以单价；“默认自建、用户主动要求时才云端重转”可以把这笔费用限制在少数复杂文件上。

维护内容：系统与依赖更新、证书续期、备份是否成功的告警、微信隐私接口和类目规则变化、微信认证年审、支付证书或公钥轮换。

扩容顺序，每一步都不改业务代码：先把同一台服务器纵向升配；再把 Worker 放到独立服务器；再换托管数据库；预览图需要时再加 CDN。

## E. 分阶段实施与多 Agent 协作

### E.1 阶段

### E.2 第一个可端到端验证的切片

只做这些：PDF、A4、黑白、单面、固定单价、到店自提、一个商品。

流程：上传 → 读取页数和预览 → 用户确认 → 下单 → 支付 → 后台收到订单并有声音提醒 → 下载确认版文件 → 店员更新状态 → 用户看到待自提和取件码。

### E.3 分工

按代码量估计，大约七成以上可以交给低成本编程 Agent。金额、权限、文件访问、订单状态机这大约三成决定系统能不能营业，必须由强模型编写，或由架构负责人逐行审查。

架构负责人亲自负责：

- 仓库骨架、编码约定、CI、接口契约基线、数据库 schema 和迁移顺序。
- 计价引擎和黄金测试向量。
- 订单状态机、支付、退款、对账。
- 身份认证、权限框架、文件访问控制。
- Worker 沙箱和转换安全。
- 部署、备份、密钥管理。
- 所有涉及金额、权限、文件访问的合并请求审查，以及最终集成验收。

适合低成本 Agent 并行：

- 小程序页面：上传、预览、参数、购物车、订单列表和详情、地址。基于 Mock 开发。
- 后台页面：价格配置、装订、证件照规格、配送、店铺设置、订单列表、统计。
- 证件照排版纯函数和裁剪组件。规格和测试用例由架构负责人给定。
- 打印就绪 PDF 的变换。变换规格和测试 PDF 由架构负责人给定。
- 配送费计算、统计查询、保留期清理任务。
- 测试：端到端场景、按权限矩阵生成的越权用例、转换回归语料比对。
- 模块说明和店员操作手册。

产品负责人参与：

- 提供真实样本文档、打印设备和经营参数。
- 审定计价黄金向量。审定过的期望值才是正确答案。
- 推进主体、认证、商户号、备案。
- 真实环境验收和店员演练。

| 波次 | 执行者 | 内容 |
|---|---|---|
| 0 | 架构负责人 | 仓库骨架、契约、schema、CI、模拟微信支付、部署脚本 |
| 1 | 4 到 6 个 Agent，加架构负责人 | Agent：小程序页面、后台常规页面、排版引擎、打印就绪变换、转换适配器。架构负责人：订单和支付核心 |
| 2 | 架构负责人主导 | 把最小闭环串起来，补端到端测试 |
| 3 | 多个 Agent，加审查 | 退款由架构负责人做。配送、统计、通知、清理任务交给 Agent |

### E.5 避免冲突和保证质量的规则

- **契约优先。** 先合并契约变更（zod schema、OpenAPI、Mock），前后端再并行。
- **目录所有权。** 每张任务卡写明可以修改的目录。跨目录改动拆成多个合并请求。
- **受保护路径。** 计价、支付、退款、订单状态机、身份、文件访问、数据库迁移、CI 配置，由 CODEOWNERS 强制架构负责人审核。
- **依赖和迁移串行。** Agent 不自行新增依赖，不自行生成迁移。在合并请求里申请，由架构负责人统一处理，避免 lockfile 和迁移序号冲突。
- **注册表不集中在一个文件。** 路由、菜单、权限点按模块一个文件，启动时自动收集。
- **小变更加门禁。** 一个任务一个合并请求，并附测试。类型检查、lint、单元测试、集成测试、契约检查、端到端冒烟都通过后才进入审查。
- **黄金测试定义正确性。** 计价向量、排版坐标、转换语料、权限矩阵由架构负责人和产品负责人审定。实现者不得修改期望值。
- **隔离工作区。** 每个 Agent 使用独立分支或工作树，并经常把主干变基进来。
- **节省上下文。** 仓库保留一份 200 行以内的 `AGENTS.md`（命令和规则）、一页 `ARCHITECTURE.md`、每项决策一页 ADR、任务卡只列必读文件。Agent 不全库扫描。

任务卡示例：

```text
任务：T-301 证件照排版引擎
目标：实现 layoutSheet(paper, spec, rules) 纯函数，单位毫米
可修改：packages/layout/**
禁止修改：packages/contracts/**、数据库迁移、lockfile
必读：docs/adr/0007-photo-layout.md、packages/layout/README.md
接口：packages/contracts/photo.ts（已冻结。需要修改时先提契约变更）
验收：fixtures/layout/*.json 全部通过；覆盖旋转、边距、间距、指定数量、套餐跨页
完成定义：CI 全绿；合并请求描述附自查清单和示例输出截图
```

### E.6 测试与上线验收

- **单元测试：** 计价、排版、状态机。包含第 B.4 节的性质测试。
- **集成测试：** API、PostgreSQL、模拟微信支付。覆盖验签、加密通知、重放、乱序到达、超时后支付成功。
- **契约测试：** 前端 Mock 与服务端 schema 一致。
- **端到端：** 管理后台用 Playwright。小程序用 miniprogram-automator 做冒烟，另附真机清单。
- **转换回归：** 样本语料比较页数和页面像素。升级 LibreOffice 或字体后必须重跑。
- **实物验收：** 证件照尺寸测量，容差由产品负责人确认。同时检查 A3、双面、黑白输出。
- **安全测试：** 越权矩阵、恶意文件样本、重复通知、重复退款、登录限流。
- **真实环境：** 0.01 元支付和退款、多机型真机、店员按作业单完整走一遍、备份恢复演练。通过后用熟客小范围试营业。

开发环境的模拟测试不能替代真实支付、真实打印和真实交付验收。

## F. 正式开发前需要确认的问题

### F.1 必须由产品负责人确认

这些问题会改变架构、计价数据结构或合规路径。确认前不把它们当成事实，也不开始依赖它们的实现。

| # | 问题 | 为什么必须确认 |
|---|---|---|
| 1 | 经营主体是个体工商户还是企业；小程序 AppID 的主体和认证状态；商户号进度 | 决定能否开通支付、备案主体是谁、何时能做真实联调 |
| 2 | 云厂商偏好、是否已有云账号、是否已有备案域名 | 决定部署和备案路径 |
| 3 | 上线后由谁维护系统，能接受多少运维工作 | 决定采用方案 A，还是更省运维的方案 B 或 C |
| 4 | 预估日订单量和峰值，门店是否靠近学校或政务中心 | 决定服务器规格和转换并发 |
| 5 | 双面按“面”还是按“张”计价；奇数页的空白背面是否计费 | 计价引擎的核心口径 |
| 6 | 计价模式是每个规格组独立配置，还是全店统一 | 价格配置的数据结构 |
| 7 | 整档优惠出现跳变时，是否启用封顶保护 | 影响顾客实际支付金额 |
| 8 | 是否接受把用户文档交给第三方云服务转换；可接受的每页转换预算 | 决定默认转换方案和隐私政策文本 |
| 9 | 能否提供 30 到 50 份脱敏的真实文档，以及店内 Word 或 WPS 打印出来的对照结果 | 转换方案验证的前提 |
| 10 | 证件照打印机型号、相纸规格、是否支持无边距；能否配合打印校准页并测量 | 证件照尺寸精度的前提 |
| 11 | 配送区域用直线距离分档、指定小区或楼栋名单，还是必须用地图多边形 | 决定是否引入地图服务和授权费用 |
| 12 | 是否允许商家因文件问题或违规内容主动退款、拒单 | 需求未覆盖、经营上需要的能力 |
| 13 | 店员是否必须按订单分配可见范围 | 决定权限模型复杂度 |
| 14 | 是否需要开发票；首版线下开票是否可接受 | 影响订单要不要收集抬头 |
| 15 | 能否把现有测试项目推送到私有仓库 | 才能评估哪些代码可以复用 |

### F.2 建议默认，确认或修改即可

这些可以合理假设。产品负责人不另行指示时，按此执行，并写入架构决策记录。

| 事项 | 建议默认 |
|---|---|
| 金额精度 | 整数“分”。单价不允许小于 1 分 |
| 阶梯分摊 | 按面数比例，最大余数法 |
| 订单支付有效期 | 15 分钟，与微信 `time_expire` 对齐，超时自动关单 |
| 购物车 | 最多 20 项。未下单文件保留 7 天，过期后重新上传 |
| 文件限制 | 单文件不超过 50 MB、不超过 500 页。单次最多选择 9 个文件 |
| 页码语法 | `1-3,5,8-`。`8-` 表示从第 8 页到最后一页 |
| 缩放与方向 | 等比缩小到所选纸张，自动旋转，居中，不放大 |
| 双面 | 长边翻转。每一份独立从新纸开始 |
| 黑白订单 | 打印文件转为灰度，降低误用彩色墨水的可能 |
| 证件照输出 | PDF，页面为相纸精确尺寸，300 DPI。有效 DPI 低于 300 提醒，低于 200 强提醒 |
| 取件 | 每单 4 到 6 位取件码，店员核销后完成 |
| 价格变更 | 购物车结算时重算并提示。已创建订单在支付有效期内保持原价 |
| 通知 | 店员：后台声音提醒加企业微信群机器人。用户：订阅消息，用于待取件和配送中 |
| 后台登录 | 账号密码，加登录限流。管理员可选 TOTP |
| 文件保留 | 订单文件完成后 30 天。证件照完成后 7 天。可配置 |
| 部分退款 | 不退配送费，不追溯补收运费。整单退款包含配送费 |
